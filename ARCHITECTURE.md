# Backend Architecture

> **Status:** Current implementation reference  
> **Last reviewed:** 2026-09-05  
> **Audience:** Frontend developers, backend developers, QA and technical leads

This document describes the behavior currently implemented in the NestJS backend. It is the integration contract for clients. When this document conflicts with a future implementation, update the contract and the corresponding code together.

## 1. System Overview

### 1.1 Purpose and scope

The backend is an education and course-operation API. It provides:

- User registration, login, account lookup and logout.
- Role and endpoint-permission administration.
- Course, classroom and enrollment management.
- Lead, invoice and payment management.
- Module shells for conversations, messages and notifications.
- MongoDB persistence with audit metadata and soft deletion support.

The application is a single deployable NestJS process. It is not currently split into microservices and it does not expose a WebSocket gateway.

### 1.2 Architecture style

The project uses a **modular monolith** with a layered flow:

```text
HTTP client
    |
    v
NestJS route/controller
    |
    +--> global ValidationPipe
    +--> global JwtAuthGuard (unless @Public())
    +--> permission check: HTTP method + route path
    v
Application service
    |
    v
Mongoose model/repository
    |
    v
MongoDB

Successful controller result
    |
    v
TransformInterceptor -> { statusCode, message, data }
```

Cross-cutting behavior is configured in `src/main.ts` and `src/app.module.ts`:

- Global prefix: `/api`.
- URI versioning: `/v1` and `/v2` are configured as default versions.
- Effective API prefix: `/api/v1/...` for current controllers.
- Global `ValidationPipe` validates DTOs. No global `whitelist` or `transform` option is configured.
- Global JWT authentication and response transformation.
- CORS allows credentials and reflects the requesting origin (`origin: true`).

## 2. Database & Data Model

### 2.1 Persistence conventions

- MongoDB ObjectIds are used for document identifiers and references.
- All Mongoose schemas use `timestamps: true`, so `createdAt` and `updatedAt` are generated by Mongoose.
- The MongoDB connection is configured from `MONGO_URL`.
- The connection installs `mongoose-delete` with `overrideMethods: 'all'` and `deletedAt: true`. Treat delete operations as soft-delete capable; clients should not assume a deleted record is physically removed.
- Audit fields `createdBy`, `updatedBy` and `deletedBy` are embedded objects containing `_id` and `email` where defined.
- Most schema fields are not marked `required`; request DTO validation is therefore the first contract to consult for required input.
- Passwords and refresh tokens are server-side sensitive fields. A frontend must never display or persist them.

### 2.2 Entity summary and relationships

| Entity | Important fields | Relationships |
| --- | --- | --- |
| `User` | `name`, `email` (unique), `password`, profile fields, `status`, `refreshToken` | Many users belong to one `Role`; `Lead.consultant_id` and `Classroom.teacher_id` reference users |
| `Role` | `name`, `description`, `isActive`, `permissions[]` | One role has many `Permission` references; many users can share a role |
| `Permission` | `name`, `path`, `method`, `module` | Referenced by many roles |
| `Course` | `name`, `description`, `level`, `duration`, `price`, `status` | One course can have many classrooms |
| `Classroom` | `course_id`, `teacher_id`, `room`, `class_name`, capacity/time fields, `status` | Belongs to one course and one teacher; has many enrollments |
| `Enrollment` | `student_id`, `class_id`, `register_date`, `status` | Belongs to one student and one classroom; may have invoices |
| `Invoice` | `enrollment_id`, `amount`, `discount_amount`, `final_amount`, `status` | Belongs to one enrollment; may have payments |
| `Payment` | `invoice_id`, `payment_method`, `payment_date` | Belongs to one invoice |
| `Lead` | contact fields, `course_name`, `consultant_id`, `status`, `note` | Optionally assigned to one consultant/user |

```text
Role 1 --- * User
Role * --- * Permission
Course 1 --- * Classroom
User 1 --- * Classroom (teacher)
User 1 --- * Enrollment (student)
Classroom 1 --- * Enrollment
Enrollment 1 --- * Invoice
Invoice 1 --- * Payment
User 1 --- * Lead (consultant)
```

## 3. Authentication & Authorization

### 3.1 Authentication model

Authentication uses short-lived JWT access tokens plus a rotating refresh token:

- Access token: returned in the login/refresh JSON response; sent in the `Authorization` header.
- Refresh token: stored by the server in an HttpOnly cookie named `refresh_token`; it is not returned as JSON.
- Access and refresh secrets are separate environment variables: `JWT_ACCESS_TOKEN_SECRET` and `JWT_REFRESH_TOKEN_SECRET`.
- Expiration values are read from `JWT_ACCESS_EXPIRE` and `JWT_REFRESH_EXPIRE` and interpreted as seconds.
- Passwords are checked with bcrypt. Invalid credentials return `401 Unauthorized`.

### 3.2 Login and token flow

```text
1. POST /api/v1/auth/login with { username, password }.
2. LocalAuthGuard validates credentials through AuthService.
3. Backend signs an access JWT and a refresh JWT.
4. Backend stores the refresh JWT against the user.
5. Backend sets refresh_token as HttpOnly cookie and returns access_token + user.
6. Client sends access_token as Bearer token on protected requests.
7. On access-token expiry, client calls GET /api/v1/auth/refresh with credentials.
8. Backend verifies the cookie and stored token, rotates it, clears the old cookie,
   sets a new cookie and returns a new access_token + user.
9. POST /api/v1/auth/logout clears the stored token and cookie.
```

Request example:

```http
POST /api/v1/auth/login
Content-Type: application/json

{
  "username": "user@example.com",
  "password": "your-password"
}
```

Protected request example:

```http
GET /api/v1/auth/account
Authorization: Bearer <access_token>
```

For browser clients, use `credentials: 'include'` or `withCredentials: true` for login, refresh and logout so the refresh cookie is sent. The access token remains client-managed; the refresh token should remain inaccessible to JavaScript.

### 3.3 Authorization: permission-based RBAC

The global `JwtAuthGuard` first authenticates the JWT and then loads permissions from the user's role. Access is granted when one permission matches:

```text
permission.method === request.method
AND
permission.path === request.route.path
```

The authenticated user object contains:

```json
{
  "_id": "ObjectId",
  "name": "string",
  "email": "string",
  "role": { "_id": "ObjectId", "name": "string" },
  "permissions": [
    { "_id": "ObjectId", "name": "string", "path": "/api/v1/users", "method": "GET", "module": "users" }
  ]
}
```

`@Public()` is used for registration, login and refresh. Auth endpoints are also explicitly allowed by the guard's `/api/v1/auth` exception. `@SkipCheckPermission()` exists for routes that should bypass the permission comparison, but it is not a role system by itself.

Important: permissions are path-sensitive. Store the exact route path expected by the guard, including parameter notation used by Express/Nest (for example `/api/v1/users/:id`), and use uppercase HTTP methods.

## 4. API Specification & System Flow

### 4.1 Base URL and versioning

```text
Development base URL: http://localhost:<PORT>
API base URL:         http://localhost:<PORT>/api/v1
```

`PORT` is read from the environment. Controllers use resource paths such as `/users`, so the effective endpoint is `/api/v1/users`.

### 4.2 Standard success response

Every successful controller response passes through `TransformInterceptor`:

```json
{
  "statusCode": 200,
  "message": "Get all courses",
  "data": {}
}
```

`message` is the controller's `@ResponseMessage` value and may be an empty string where no decorator is present. `data` contains the original service result. For login, `data` contains `access_token` and `user`; for logout, it contains the string `"ok"`.

### 4.3 Main route matrix

All routes below are protected unless marked **Public**. The exact role is not hard-coded in controllers; access is determined by the user's stored endpoint permission.

| Method | Endpoint | Access | Purpose |
| --- | --- | --- | --- |
| POST | `/auth/login` | Public | Login with local credentials |
| POST | `/auth/register` | Public | Register a user |
| GET | `/auth/account` | Auth + permission | Get current user and resolved permissions |
| GET | `/auth/refresh` | Public + refresh cookie | Rotate refresh token and issue access token |
| POST | `/auth/logout` | Auth + permission | Revoke refresh token and clear cookie |
| GET/POST/PATCH/DELETE | `/users`, `/users/:id` | Permission | User CRUD |
| GET/POST/PATCH/DELETE | `/roles`, `/roles/:id` | Permission | Role CRUD |
| GET/POST/PATCH/DELETE | `/permissions`, `/permissions/:id` | Permission | Permission CRUD |
| GET/POST/PATCH/DELETE | `/courses`, `/courses/:id` | Permission | Course CRUD |
| GET/POST/PATCH/DELETE | `/classrooms`, `/classrooms/:id` | Permission | Classroom CRUD |
| GET/POST/PATCH/DELETE | `/enrollments`, `/enrollments/:id` | Permission | Enrollment CRUD |
| GET/POST/PATCH/DELETE | `/invoices`, `/invoices/:id` | Permission | Invoice CRUD |
| GET/POST/PATCH/DELETE | `/payments`, `/payments/:id` | Permission | Payment CRUD |
| GET/POST/PATCH/DELETE | `/leads`, `/leads/:id` | Permission | Lead CRUD |
| GET/POST/PATCH/DELETE | `/conversations`, `/conversations/:id` | Permission | Module scaffold; verify implementation |
| GET/POST/PATCH/DELETE | `/messages`, `/messages/:id` | Permission | Module scaffold; verify implementation |
| GET/POST/PATCH/DELETE | `/notifications`, `/notifications/:id` | Permission | Module scaffold; verify implementation |

The CRUD route pattern is the intended module surface. Consult the controller before generating a client for a specific module because route parameter placement and update signatures are not fully uniform in the current code.

### 4.4 List, filtering and pagination

CRUD list endpoints accept:

| Query parameter | Meaning | Example |
| --- | --- | --- |
| `current` | Page number passed to the service | `1` |
| `pageSize` | Page size passed to the service | `10` |
| Additional query fields | Parsed by `api-query-params` for filtering/sorting/search behavior | `?status=OPEN` |

Example:

```http
GET /api/v1/courses?current=1&pageSize=10&status=ACTIVE
Authorization: Bearer <access_token>
```

The exact list metadata shape is service-specific. Frontend pagination code should inspect the returned `data` shape for each module rather than assuming a single `{ items, meta }` format.

### 4.5 Core business flows

#### A. Course delivery and enrollment

1. An authorized operator creates a course with `POST /courses`.
2. An authorized operator creates a classroom with `course_id`, teacher, schedule, capacity and status `OPEN`.
3. A student/user is enrolled through `POST /enrollments` with `student_id` and `class_id`.
4. The enrollment starts with the status appropriate to the DTO/business rule, commonly `WAITING_PAYMENT`.
5. An invoice is created for the enrollment with amount, discount and final amount.
6. A payment is recorded against the invoice using `invoice_id`, payment method and payment date.
7. Enrollment, invoice and classroom status transitions are performed through their respective APIs; the backend schemas do not currently define a single cross-module transaction endpoint.

#### B. Permission administration

1. Create or update `Permission` records with the exact method/path pair.
2. Assign permission ObjectIds to a `Role` through the role API.
3. Assign the role to a `User`.
4. The next authenticated request resolves role permissions in `JwtStrategy`.
5. If no exact pair matches, the API returns `403 Forbidden`.

#### C. Lead assignment

1. Capture a lead with contact information and the requested `course_name`.
2. An authorized operator updates `consultant_id`, `status` and `note`.
3. The frontend uses the lead status string for its workflow; no enum is enforced in the current schema.

### 4.6 Current contract caveats

- The configured versioning supports `/api/v1` and `/api/v2`, but controllers do not declare per-route versions. Use `/api/v1` as the current documented base and verify `/v2` behavior before adopting it.
- Some CRUD controllers use `PATCH` with `:id` in the route while their method signature does not visibly accept a `@Param('id')`; confirm the corresponding service/DTO behavior before relying on path-based updates.
- Conversation, message and notification entities are empty placeholder classes, so their API should not be treated as production-ready.
- Schema fields such as monetary values and capacity are currently represented inconsistently (`price` and `max_student` are strings, invoice amounts are numbers). Preserve the API's actual types in client models.
- No explicit file upload, WebSocket, webhook or OAuth2 integration is configured in the inspected application.

## 5. Error Handling & Status Codes

### 5.1 HTTP statuses

| Status | Meaning | Frontend action |
| --- | --- | --- |
| `200 OK` | Successful read/update/action | Consume `data` |
| `201 Created` | Successful creation | Consume created resource |
| `400 Bad Request` | Invalid request, DTO validation failure or invalid refresh token | Show validation/business error; refresh token failure should return to login |
| `401 Unauthorized` | Missing/invalid/expired access token or invalid credentials | Attempt refresh once, then clear auth state |
| `403 Forbidden` | Authenticated user lacks endpoint permission | Hide/disable action and show access-denied state |
| `404 Not Found` | Resource or route not found | Show missing-resource state |
| `409 Conflict` | Duplicate/conflicting resource where raised | Ask user to resolve conflict |
| `500 Internal Server Error` | Unexpected server failure | Show generic retry message and log correlation data if available |

### 5.2 Validation and error payloads

Success responses have the stable wrapper shown above. NestJS exception responses are not transformed by `TransformInterceptor` in the current implementation, so error bodies may follow Nest's native format rather than `{ statusCode, message, data }`.

Typical examples:

```json
{
  "statusCode": 401,
  "message": "Token không hợp lệ hoặc không có bearer token ở header",
  "error": "Unauthorized"
}
```

```json
{
  "statusCode": 403,
  "message": "Bạn không có quyền truy cập vào endpoint này",
  "error": "Forbidden"
}
```

Validation errors may return `message` as an array of constraint messages. Frontend code should support both a string and an array.

### 5.3 Application error codes

The current backend does not define a separate machine-readable `code` field. Use HTTP status plus message until internal error codes are introduced.

| Current identifier | HTTP status | Message/condition |
| --- | --- | --- |
| `AUTH_INVALID_CREDENTIALS` | 401 | `Username/Password is not correct` |
| `AUTH_INVALID_ACCESS_TOKEN` | 401 | Invalid or missing Bearer token |
| `AUTH_FORBIDDEN_ENDPOINT` | 403 | User lacks matching method/path permission |
| `AUTH_INVALID_REFRESH_TOKEN` | 400 | `Invalid refresh token. Vui lòng đăng nhập lại.` |
| `VALIDATION_ERROR` | 400 | DTO validation constraint failure |
| `RESOURCE_NOT_FOUND` | 404 | Service cannot find requested record |
| `RESOURCE_CONFLICT` | 409 | Duplicate or conflicting data, such as an existing unique email |

These names are documentation-level aliases, not fields currently emitted by the API.

## 6. Integration Guidelines for Frontend

### 6.1 Client state to maintain

| State | Storage/lifetime | Notes |
| --- | --- | --- |
| `accessToken` | In-memory preferred; renew with refresh cookie | Send as Bearer token |
| `currentUser` | Auth store/in-memory, optionally persisted without secrets | Includes `_id`, `name`, `email`, `role`, `permissions` |
| `refresh_token` | HttpOnly browser cookie managed by browser | Do not read or store in localStorage |
| `isAuthenticated` | Derived from token/user state | Reset after failed refresh/logout |
| `permissions` | Derived from `currentUser.permissions` | Gate UI actions, but backend remains authoritative |
| Resource lists | Query cache/store | Keep `current`, `pageSize`, filters and returned metadata together |
| Request state | Per feature | Track loading, success, validation and authorization errors separately |

### 6.2 HTTP client rules

```ts
const api = axios.create({
  baseURL: `${API_ORIGIN}/api/v1`,
  withCredentials: true,
});

api.interceptors.request.use((config) => {
  const token = authStore.getAccessToken();
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});
```

Recommended response handling:

1. Read successful business data from `response.data.data` when using Axios.
2. Preserve `response.data.message` for toast/logging text.
3. On the first `401`, call `/auth/refresh` with credentials and retry the original request once.
4. Prevent multiple simultaneous refresh calls with a single-flight queue.
5. On refresh failure, clear the access token and route the user to login.
6. Treat `403` as a permission state, not as an authentication-expired state.

### 6.3 CORS and cookies

The server enables CORS with credentials and reflects origins. The frontend must:

- Send credentials for auth cookie flows.
- Use HTTPS in production and configure cookie `SameSite`/`Secure` policy appropriately for the deployment topology.
- Ensure the frontend origin is an allowed deployment origin before production hardening.
- Never expose `refresh_token` to application JavaScript.

### 6.4 Uploads and real-time communication

No multipart upload handler, storage adapter, WebSocket gateway or Server-Sent Events endpoint is currently configured. Do not implement file or real-time client flows against this backend until a concrete endpoint contract is added.

### 6.5 Frontend integration checklist

- [ ] Configure the environment-specific origin and `/api/v1` base path.
- [ ] Send `Authorization: Bearer <accessToken>` for protected requests.
- [ ] Enable credentials for login, refresh and logout.
- [ ] Keep the refresh token out of localStorage and application state.
- [ ] Implement one-refresh-and-retry behavior for `401` responses.
- [ ] Handle `403` separately from `401`.
- [ ] Unwrap successful payloads from `data`.
- [ ] Support error `message` as either string or array.
- [ ] Send `current` and `pageSize` for list screens and retain active filters.
- [ ] Use ObjectId strings for referenced fields such as `course_id`, `class_id`, `invoice_id` and `role`.
- [ ] Use only the documented classroom/enrollment enum values.
- [ ] Do not assume status values for course, lead, invoice or payment are enums yet.
- [ ] Confirm route and DTO details for conversation, message, notification and database utility modules before building screens.
- [ ] Keep permission checks in the UI aligned with `method + path`, while treating server responses as authoritative.
